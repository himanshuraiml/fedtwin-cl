## 2. What the spike pilot actually validated

Running `colab_pilot_spike.ipynb` end to end (see Section 3) does the following, all with real, executed code:

1. Implements the FedCAT global mask registry, the heterogeneity-aware sparsity controller (Eq. 2), staleness-free synchronous aggregation, and masked inference (Eq. 7) from scratch, in NumPy.
2. Implements Drift-Triggered Task Segmentation (Section 4.3, Eqs. 3–4) as an actual Page-Hinkley detector running online against a synthetic health-indicator stream.
3. Implements Cross-Twin Fault Relevance scoring (Section 4.7, Eq. 6): a signature is computed and broadcast on every commit, and every other site checks its own recent trajectory against the broadcast registry every round.
4. Runs six methods (FedAvg, FedAvg+EWC, FedCAT with oracle task boundaries, FedTwin-CL without CTFR, full FedTwin-CL, and a Centralized Task-Isolated upper bound) across three synthetic benchmark configurations standing in for Fed-Twin-CMAPSS, Fed-Twin-FEMTO, and Fed-Twin-MIMII.
5. **Directly tests Theorem 5.1 / Proposition 5.2**, not just runs the code and hopes: Section 8 of the notebook decomposes measured Fleet Backward Transfer by whether a task was actually protected by a DTTS commit. The result (also asserted, not just printed): tasks that got a mask show **exactly** zero backward transfer; tasks DTTS failed to catch show real, uncontrolled forgetting. This is the empirical signature the theorem predicts, and it only appeared after fixing several real implementation bugs (see Section 5).

What it does **not** validate: absolute performance against real degradation signals, the real TCN-Nano/DS-CNN-S architectures, real communication payloads at the real parameter counts, or CTFR's real-world precision (the synthetic signature's false-positive rate is visibly high and is called out as a known limitation in the notebook itself).

## 5. Bugs found and fixed (14 total, spike + real pilot)

Bugs 1–7 were found building the synthetic spike; bugs 8–14 were found building the real pilot, several by reproducing symptoms this exact list predicted:

1. **Time-scale mismatch.** An early version called the per-round data-sampling function once per local SGD step, so a single round's inner training loop could silently cross several true task boundaries before the once-per-round drift check ever saw them. Fixed by strictly separating "advance stream time" (once per round) from "sample a minibatch" (many times per round, from whichever task is fixed for that round).
2. **Commit-time scoring used post-drift weights.** Filter-importance scoring for a commit was originally computed after that round's local training had already started pulling weights toward the *new* task, so the mechanism was protecting a blend of old- and new-task weights rather than the old task. Fixed by scoring and committing from the pre-training snapshot, before any new-task gradient step.
3. **Unmasked evaluation of committed tasks.** The single biggest source of spurious "forgetting" in early runs: evaluating a completed task's performance using the *full*, still-changing shared backbone, rather than only that task's own committed filters (Eq. 7's masked inference). A perfectly frozen set of weights can still produce a different output over time if the forward pass also reads other, later-repurposed columns.
4. **An unmasked shared output bias.** Even after fixing (3), a single scalar output bias shared by all tasks was still being trained for masking methods, and kept drifting with every later task — contaminating every earlier task's masked output despite its own filters being provably frozen. Fixed by freezing the bias too, for masking methods only.
5. **Overwriting instead of accumulating masks on over-segmentation.** When DTTS triggers more than once while the ground-truth task hasn't actually changed yet (a real, expected behavior — see Remark 5.1), each commit protects a different slice of columns; tracking only the most recent commit's mask per task silently dropped the earlier commit's columns from evaluation, even though they remained frozen in the registry.
6. **Non-deterministic seeding via Python's `hash()`.** Used to derive a per-method random seed; `hash()` on a string is randomized per process by default, which made every run non-reproducible **and** gave different methods uncontrolled, unrelated initial weights instead of a fair, controlled comparison. Fixed by seeding from each method's fixed position in an ordered list instead.
7. **An unlearnable classification label.** The synthetic MIMII-style benchmark's binary label was originally built purely from a single scalar health-indicator value shared across an entire batch, carrying no information about the input features at all — AUC was stuck at chance (0.5) for every method regardless of training, because there was nothing in the input for a classifier to learn. Fixed by deriving the label from the same per-sample fault mapping used for the regression benchmarks (a median split), keeping the health indicator as a purely separate drift-detection signal.
8. **(C-MAPSS) FD002 needs per-operating-condition normalization, not global stats.** Naively reusing FD001's single-condition mean/std on FD002 (six operating regimes, wildly different raw sensor ranges) caused catastrophic blowups (FPS in the tens of thousands), and only for the 8 FD002-sourced sites — the per-site pattern of the blowup was the actual diagnostic clue. Fixed with k-means (k=6) on the operating-setting channels, then per-regime z-scoring.
9. **(C-MAPSS) EWC gradient clipping happened before the EWC penalty gradient was added**, leaving the penalty term unbounded and overflowing to NaN on real (less uniform) gradients; because FedAvg-EWC uses full-network cross-site averaging, one site's NaN silently contaminated all 24 sites the next round. Fixed by adding the penalty gradient before clipping, and separately clipping the Fisher-diagonal calibration gradient before squaring it.
10. **(FEMTO) `np.convolve(..., mode="same")` zero-pads at sequence boundaries**, fabricating a sharp fake "recovery" in the health indicator over the last ~8 samples of every bearing — exactly where real degradation is fastest. Fixed with an edge-safe `pandas.Series.rolling(window=15, min_periods=1, center=True).mean()`.
11. **(FEMTO) Oracle boundary triggered on every noisy stage oscillation**, not just genuine milestones, starving device capacity on spurious early commits. Fixed by tracking `max_stage_reached[i]` per site and only triggering when the true stage strictly exceeds it.
12. **(FEMTO) Masks kept accumulating into the same stage key even after that stage's eval-at-commit snapshot was already recorded** (when oscillation caused a stage value to recur), corrupting PROTECTED-task FBWT away from exact zero. Fixed with a `stage_already_measured` guard before allowing further mask growth for an already-scored stage.
13. **(FEMTO) Ground-truth stage assigned by health-indicator VALUE quantile instead of TIME tercile.** On real noisy vibration data this let "stage 0" get measured and frozen using pure random-init weights within round 0 itself — a `+0.000000` result that looked correct but was measuring nothing. Fixed by switching to time-based terciles; also had to recalibrate DTTS's $\lambda_{\text{PH}}$ from 0.7 (C-MAPSS-tuned) down to 0.15 for FEMTO's noisier real signal.
14. **(MIMII) Extracted audio features were never normalized.** RMS (~O(200)) and zero-crossing rate (~O(0.1)) live on wildly different scales; caught proactively before running (from the C-MAPSS FD002 experience, bug #8) rather than after a failure. Fixed by adding per-site pooled z-score normalization in `preprocess_mimii.py` before saving.

If a future re-implementation (deeper architecture, additional datasets) reproduces any of these symptoms — forgetting where none should exist, AUC/metric blowups isolated to specific sites, a fake end-of-sequence "recovery," non-reproducible runs, or a `+0.000000` result that appears suspiciously early — check this list first.

### 8.2 Real FedProx and Centralized Task-Isolated baselines (reviewer items 1–2)

`real_data/real_fedprox_centralized.py` implements both baselines generically against any of the three existing pipeline modules (`real_pipeline_{cmapss,femto,mimii}`), reusing their validated backbone/loss/clipping/stream code unchanged rather than reimplementing it a third time.

**FedProx** (mu = 0.01, a standard small-drift-penalty default, not swept): identical training dynamics to the existing dense "fedavg" method, with the proximal gradient `mu * (theta - theta_global_at_round_start)` added to every local step's gradient before clipping (mirroring the EWC-penalty-before-clipping fix, bug #9, since an unbounded prox term risks the same NaN-then-fleet-wide-contamination failure mode on real gradients).

| Benchmark | FedProx FPS | FedProx FBWT |
|---|---|---|
| Fed-Twin-CMAPSS | −0.1343 ± 0.0855 | +0.0039 ± 0.1543 |
| Fed-Twin-FEMTO | −0.1010 ± 0.0756 | +0.0821 ± 0.1257 |

FedProx's FBWT is small and near-zero on both benchmarks (closer to zero than plain FedAvg's on Fed-Twin-FEMTO, slightly better than FedAvg's on Fed-Twin-CMAPSS too), consistent with the proximal term doing its intended job of damping client drift, though it remains a dense, non-forgetting-aware method by construction (no masking, no zero-forgetting guarantee) and its absolute FPS is still well short of the masking methods' guarantee, just like plain FedAvg.

**Centralized Task-Isolated**: one freshly initialized model per (site, ground-truth-stage) pair, trained only on that pair's own real windows (an 80/20 within-stage train/eval split, so "eval" is genuinely held out), no federation, no masking, ever. Forgetting-free by construction (FBWT = 0.0 exactly, not measured — no shared parameters exist for a later task to overwrite).

**Bug #15 (training-budget artifact, not a code-correctness bug): Centralized Task-Isolated was first tried at 300 SGD steps/task and badly undertrained.** A direct diagnostic on one representative (site, stage) pair showed the *training-set* metric itself was still far from converged at 300 steps (train_metric = −0.239) versus fully converged by 3000 steps (train_metric ≈ −0.000, eval_metric ≈ −0.009). An undertrained "upper bound" is not a real upper bound: at 300 steps, Centralized's own raw FPS (−0.161 cmapss / −0.116 femto) was *worse* than a trivial persistence-predictor floor (≈ −0.00004, both benchmarks) — i.e., the supposed ceiling was scoring below the supposed floor, which would have silently produced nonsensical normalized-FPS values without an obvious symptom (no NaN, no crash, just a quietly wrong ceiling). Caught by direct inspection before trusting the number, not after. Fixed by raising `CENTRALIZED_STEPS` to 3000, which produces a converged per-task model (confirmed by inspecting train-set metric, not just eval-set metric) and a properly higher Centralized FPS on both benchmarks.

| Benchmark | Centralized FPS (3000 steps) | Centralized FBWT |
|---|---|---|
| Fed-Twin-CMAPSS | −0.0484 ± 0.0215 | 0.0000 (exact, by construction) |
| Fed-Twin-FEMTO | −0.0412 ± 0.0381 | 0.0000 (exact, by construction) |

**A second, more fundamental finding survived the fix above and is reported as genuine, not a bug**: even after confirming Centralized is properly converged, its raw FPS (−0.0484 / −0.0412) is still *worse* (more negative) than the trivial persistence-predictor floor (−0.0000417 / −0.0000237) on both real regression benchmarks. This is not undertraining — it is a real property of how C-MAPSS/FEMTO's piecewise-linear, RUL-cap-based target is constructed: the normalized RUL target is flat at exactly 1.0 for most of an engine's/bearing's early life (confirmed directly: `rul_norm[:30]` for a representative site is `[1., 1., ..., 1.]`), so a naive "predict the same value as last observed" persistence baseline is nearly perfect almost everywhere except right at end-of-life, making it a much stronger baseline than the term "trivial floor" suggests for this specific target construction. A per-stage Centralized model, trained on only ~45–60 real windows per (site, stage) pair with a 512-channel backbone, cannot exploit that same free lunch and pays a real small-sample cost the persistence predictor does not. **Practical consequence**: Eq. 7/14's Psi normalization, as literally specified (floor = persistence predictor, ceiling = Centralized), produces a floor that exceeds the ceiling on both real regression benchmarks, so normalized Fleet Performance Score units computed this way are not currently interpretable for Fed-Twin-CMAPSS/Fed-Twin-FEMTO — this is reported honestly in Results/Discussion below rather than smoothed over, and is a genuine metric-design finding for future work, not a resolved gap.

### 8.3 Fleet Performance Score (Eq. 7/14) normalization — implemented, with the caveat above

`compute_psi_anchors()`/`psi()` in `real_fedprox_centralized.py` implement Eq. 14 literally (floor = mean persistence-predictor raw metric across sites for the two regression benchmarks, chance-level AUC = 0.5 for Fed-Twin-MIMII; ceiling = mean Centralized Task-Isolated fleet_perf_score). Computed floor/ceiling: Fed-Twin-CMAPSS floor = −0.0000417, ceiling = −0.0484; Fed-Twin-FEMTO floor = −0.0000237, ceiling = −0.0412. Because floor > ceiling on both (Section 8.2's second finding), the resulting `fps_normalized` values are still saved to the output JSON (clipped to [0, 1] as specified) but should be read as diagnostic only, not as a trustworthy normalized comparison, until the normalization's choice of trivial floor is redesigned for targets with this "long flat region" property. This is now the manuscript's honest position (Results/Discussion updated accordingly) rather than the previous "not yet implemented" gap.

### 8.4 Capacity sweep on Fed-Twin-CMAPSS and Fed-Twin-FEMTO (reviewer item 3)

`real_data/real_capacity_sweep.py` re-runs FedAvg, Oracle-Boundary Engine (`fedcat-external`), and full FedTwin-CL at 1x (512 ch, the pilot's existing width), 2x (1024 ch), and 4x (2048 ch) the TCN-Nano-lite conv channel count, scaling every device class's `CMAX` proportionally at each width (a genuinely bigger per-device capacity budget throughout, not just a bigger shared pool still throttled by an unchanged per-device ceiling).

| Benchmark | Width | FedAvg current-task metric | Oracle current-task metric | FedTwin-CL current-task metric | Gap (FedAvg − FedTwin-CL) |
|---|---|---|---|---|---|
| Fed-Twin-CMAPSS | 1x | −0.3084 | −0.5285 | −1.6873 | +1.3790 |
| Fed-Twin-CMAPSS | 2x | −0.3934 | −0.5519 | −0.8025 | +0.4091 |
| Fed-Twin-CMAPSS | 4x | −1.0157 | −0.6461 | −2.3022 | +1.2865 |
| Fed-Twin-FEMTO | 1x | −0.2579 | −5.4555 | −0.9499 | +0.6921 |
| Fed-Twin-FEMTO | 2x | −0.3041 | −6.0522 | −0.7863 | +0.4822 |
| Fed-Twin-FEMTO | 4x | −0.3446 | −8.8484 | −0.7872 | +0.4426 |

**Honest answer to the reviewer's question: the gap does not cleanly close as capacity grows, and the two benchmarks disagree with each other.** On Fed-Twin-FEMTO the gap narrows fairly steadily as width grows (0.69 → 0.48 → 0.44, roughly a 36% reduction from 1x to 4x) — some real support for the capacity-artifact hypothesis there. On Fed-Twin-CMAPSS the gap is non-monotonic and does **not** narrow overall (1.38 → 0.41 → 1.29): it shrinks sharply at 2x but *widens back past its 1x value* at 4x, driven mainly by FedAvg's own current-task metric getting markedly worse at 4x (−1.0157, its worst value in the sweep) rather than FedTwin-CL improving — i.e., at 4x width with the same fixed 40-local-steps-per-round training budget, dense FedAvg itself appears to be undertrained/destabilized by the larger parameter count, not a masking-method weakness. We report this plainly: widening the backbone is not a reliable fix for the Table 1 gap at this training-budget scale, and any future deeper-architecture pass should also re-tune the local training budget (steps, learning rate) per width rather than holding it fixed, since this sweep's fixed budget likely confounds "wider" with "relatively less-trained per parameter."

### 8.5 Compression-matched FedAvg baseline (reviewer item 4)

`real_data/real_compression_matched.py` adds a "FedAvg + top-k + quantization" condition: the same training as plain FedAvg, but each round's full dense parameter delta is compressed with the identical `kappa=0.5` top-k-by-magnitude selection and `b_q=4`-bit quantization already used for FedTwin-CL's masked uploads, before counting payload bytes.

| Benchmark | FedAvg (dense) | FedAvg + top-k + quant (NEW) | FedTwin-CL (masked + compressed) | Reduction vs. dense (old comparison) | Reduction vs. compression-matched (new, fair) | CTFR signature payload |
|---|---|---|---|---|---|---|
| Fed-Twin-CMAPSS | 112,068,480 B | 7,004,160 B | 1,653,367 B | 67.8× | **4.2×** | 21 commits × 24 B = 504 B |
| Fed-Twin-FEMTO | 80,611,200 B | 5,038,080 B | 1,558,105 B | 51.7× | **3.2×** | 15 commits × 24 B = 360 B |

**This is the single most important, and most inconvenient, finding of this pass.** Most of the previously reported ~98%+/~68–98× uplink reduction (manuscript Table 3, comparing FedTwin-CL against *dense, uncompressed* FedAvg) comes from generic top-k+quantization compression, not from masking. Once FedAvg is given the exact same compression scheme, masking's own marginal contribution over compression alone is only about **4.2× on Fed-Twin-CMAPSS and 3.2× on Fed-Twin-FEMTO** — real, and still meaningful, but nowhere near the two-orders-of-magnitude headline figure the paper currently leads with. Both comparisons are real numbers on real data and both should be reported side by side (Results table below), not one replacing the other, since they answer different questions: "vs. an undefended baseline" and "vs. a baseline given the same generic compression." The CTFR signature payload (24 bytes/commit, 6 fp32 floats per Eq. 15) is confirmed negligible in absolute terms (504 B and 360 B total over the whole 20-round, 24-site run) exactly as the manuscript already claimed, now reported as its own explicit line rather than folded into FedTwin-CL's masked total.

### 8.6 Alternative drift detector: KSWIN vs. Page-Hinkley, real Fed-Twin-FEMTO (reviewer item 5)

`real_data/real_alt_detector.py` implements a minimal from-scratch KSWIN (Kolmogorov-Smirnov Windowing: sliding window of recent health-indicator readings, two-sample KS test between the most recent sub-window and a random sample of the rest, `scipy.stats.ks_2samp`) rather than adding `river`/`scikit-multiflow` as a new dependency, and runs it head-to-head against the existing Page-Hinkley DTTS on the same real Fed-Twin-FEMTO benchmark the threshold-sensitivity study already uses.

**Bug #16 (detector-configuration finding, not a code bug): KSWIN's textbook-default significance levels (alpha = 0.01, 0.05) can never fire at this pilot's window/stat-size and 20-round-per-site horizon.** The two-sample KS test's exact null distribution has a *coarse, discrete* minimum achievable p-value for small samples — confirmed directly: `ks_2samp([0,0,0],[1,1,1])` (the most extreme possible separation for 3-sample groups) already returns p ≈ 0.0999999, not the small value continuous intuition suggests. With `window_size=10, stat_size=3` (the largest feasible stat_size given the pilot's 20-round-per-site budget, chosen to leave room for the window to fill *and* re-trigger), alpha = 0.01 and alpha = 0.05 are both strictly below that floor and the detector **cannot ever trigger, no matter how sharply the two windows differ**. We ran and report both this naive-default result and a calibrated operating point (alpha = 0.10, the minimum value that CAN ever fire at this configuration):

| Detector | Total commits | Mean tasks/site | Mean \|timing error\| (rounds, n) | Fleet FPS | Fleet FBWT | Protected n (mean FBWT) | Missed n (mean FBWT) |
|---|---|---|---|---|---|---|---|
| Page-Hinkley (lambda=0.15, operating point) | 14 | 0.583 | 3.0 (n=3) | −0.673 | −0.392 | 2 (**+0.000000**) | 46 (−0.409) |
| KSWIN, alpha=0.01 (naive default) | 0 | 0.000 | n/a | −0.464 | −0.227 | 0 (n/a) | 48 (−0.227) |
| KSWIN, alpha=0.10 (calibrated minimum-firing threshold) | 13 | 0.542 | 3.92 (n=13) | −0.972 | −0.510 | 13 (**+0.000000**) | 35 (−0.699) |

Reading this honestly: calibrated KSWIN catches almost the same *number* of total real commits as Page-Hinkley (13 vs. 14) but protects far more *distinct* site-task pairs (13 vs. only 2), meaning it distributes its commits across more genuinely different transitions rather than concentrating them (Page-Hinkley's known FEMTO conservatism, Table 2/Section 6 above). Despite protecting more tasks, KSWIN's downstream fleet FPS and FBWT are both *worse* than Page-Hinkley's, and its timing error is larger (3.92 vs. 3.0 rounds, on a much bigger sample of 13 vs. 3). **The zero-forgetting guarantee itself is reconfirmed under this second, independent detector**: every protected task under both Page-Hinkley and calibrated KSWIN shows exactly 0.000000 FBWT, direct additional evidence that Theorem 1's guarantee is detector-agnostic (it depends only on whether a task was committed, not on which detector triggered the commit) — a nice bonus validation, not just a head-to-head horse race.

### 8.7 Longer, finer-grained progressive drift sequence (reviewer item 6)

`real_data/preprocess_femto_longseq.py` regenerates Fed-Twin-FEMTO with 8 ground-truth stages (equal-duration time splits, generalizing the existing 3-way tercile split to eighths) instead of 3, saved separately as `processed/femto_sites_longseq.npz` (the original 3-stage `femto_sites.npz` is untouched). `real_data/real_longer_sequence.py` re-runs FedAvg, Oracle-Boundary Engine, and full FedTwin-CL at 50 communication rounds instead of 20, tracking per-round registry saturation ($\rho^{\text{global}}$) alongside the usual commit/FPS/FBWT bookkeeping.

| Method | Total commits | Final $\rho^{\text{global}}$ | Fleet FPS (final) | Fleet FBWT (final) |
|---|---|---|---|---|
| FedAvg | 0 | 0.000 | −0.0959 | +0.0696 |
| Oracle-Boundary Engine | 12 | **1.000** | −0.3056 | −0.0001 |
| FedTwin-CL (DTTS) | 13 | **1.000** | −0.5141 | −0.1210 |

**This directly resolves the open question Section 6/7 above flagged**: at 3 stages and 20 rounds, DTTS's real conservatism meant the fleet's mask registry never came close to filling, so Section 5.3's fleet-capacity claim was never genuinely tested under real pressure. At 8 stages and 50 rounds, both the oracle and DTTS-triggered methods drive the registry to **full saturation ($\rho^{\text{global}}=1.000$) by round 50** — real capacity pressure, not synthetic. Under that real saturation, FedTwin-CL's mean FBWT (−0.121) is noticeably worse than the oracle's (−0.0001, essentially zero): as free registry capacity runs out late in the run, DTTS-triggered commits appear to get a smaller, lower-quality slice of remaining filters than earlier commits did, a genuine capacity-pressure cost that the original 3-stage/20-round pilot was too short to ever surface. This is reported as an honest, real limitation surfaced only by testing at longer horizon and finer granularity, extending (not just confirming) Section 5.3's fleet-capacity claim.

Fed-Twin-CMAPSS was not re-run at longer/finer granularity in this pass (time-budget decision); Fed-Twin-FEMTO alone directly answers the reviewer's question since it is the benchmark DTTS is already documented as most conservative on, making it the sharpest test of capacity pressure.

Fixing `run_fedprox`/`run_compression_matched`/`run_capacity_sweep` for MIMII required generalizing three things that the cmapss/femto-only code paths had not needed: (1) `run_fedprox`'s `n_sensors`/`window` discovery, which read `sites_data[0]["windows"].shape` unconditionally — MIMII's per-site record has no `"windows"` key at all (it stores `"round_windows"`, a per-round list of variable-length clip batches), so this raised a bare `KeyError` the first time it was run against `--benchmarks mimii`, caught immediately rather than silently mis-shaping the backbone (**bug #17**, a straightforward missed-branch bug, not a subtler numerical one); (2) `real_capacity_sweep.py`'s per-width loop, which needed the same MIMII-aware stream-class lookup (`MimiiSiteStream` vs `RealSiteStream`) and `None`-metric guards (AUC is undefined for a single-class batch) already built into `real_fedprox_centralized.py`, now added there too; (3) MIMII's `minibatch()` returns a fixed per-round clip batch rather than a resampleable stream, so the capacity sweep's inner training loop was changed to reuse that fixed batch across all `LOCAL_STEPS` steps for MIMII specifically (matching `run_mimii()`'s own convention) instead of resampling every step the way cmapss/femto do.

**A genuine, first-time-in-this-project finding: Fed-Twin-MIMII's Psi normalization does NOT share the persistence-floor-exceeds-ceiling pathology found on the two regression benchmarks (Section 8.2/8.3).** Computed floor/ceiling: floor (chance-level AUC) = 0.500, ceiling (Centralized) = 0.817 — properly ordered, floor below ceiling, exactly as Eq. 14 assumes. This confirms the pathology found on Fed-Twin-CMAPSS/Fed-Twin-FEMTO is specific to targets with a long flat region (capped, piecewise-linear RUL), not a general flaw in the Eq. 14 design; a classification/AUC benchmark with a genuine chance-level floor does not have this problem.

**Compression-matched FedAvg baseline on Fed-Twin-MIMII** (`real_compression_matched.py --benchmarks mimii`): dense FedAvg total uplink 72,746,880 B; compression-matched (top-k=0.5 + 4-bit quant) 4,546,560 B (16.00× smaller, identical ratio to cmapss/femto since it is a fixed function of kappa/b_q); FedTwin-CL (masked+compressed) 940,629 B. Reduction vs. dense: 77.3×. **Reduction vs. the fair, compression-matched baseline: 4.8×** — consistent with cmapss's 4.2× and femto's 3.2×, confirming masking's fair marginal contribution (roughly three- to fivefold) is a real, benchmark-independent effect, not an artifact of one dataset's structure. CTFR signature payload: 21 commits × 24 B = 504 B (identical commit count to Fed-Twin-CMAPSS).

**Capacity sweep on Fed-Twin-MIMII** (`real_capacity_sweep.py --benchmarks mimii`, widths 1x/2x/4x): unlike either regression benchmark, the FedAvg-vs-FedTwin-CL gap on Fed-Twin-MIMII widens steadily and monotonically with width (+0.152 -> +0.177 -> +0.188, current-task AUC), the opposite direction from Fed-Twin-FEMTO's narrowing and a cleaner (monotonic) pattern than Fed-Twin-CMAPSS's non-monotonic one. The driver is visible directly in the per-method numbers: dense FedAvg's own current-task AUC improves steadily with width (0.657 -> 0.686 -> 0.693) while both masking methods plateau around 0.50-0.53. All three real benchmarks now disagree with each other on this question in three distinct ways (narrows / non-monotonic / widens), which is itself the honest answer: there is no single capacity-budget story that holds across benchmarks, and any future architecture-scale-up pass should expect to re-tune the local training budget per benchmark, not apply one fix universally.

**Alternative detector (KSWIN) and longer/finer sequence on Fed-Twin-MIMII were deliberately NOT run.** Both were scoped in the original reviewer-gap brief specifically to Fed-Twin-FEMTO (the benchmark the existing DTTS-threshold sensitivity study already centers on), not to all three benchmarks; extending them to MIMII would require materially new engineering (MIMII's `MimiiSiteStream` has no long continuous real timeline to re-segment more finely — its "rounds" are already a constructed schedule over independent real clips, not a continuously recorded signal the way cmapss/femto are) rather than a parameter change, and was judged out of scope for the time remaining in this pass. If undertaken later, the longer-sequence study in particular would need a redesigned ground-truth-stage construction for MIMII specifically, not simply a larger `n_stages` argument to an existing preprocessing function.
